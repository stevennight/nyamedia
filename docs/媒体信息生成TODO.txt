你的判断我基本同意，而且这会把方案收敛到一个更现实的方向：

```text
播放代理不负责“生成字幕”
播放代理只负责“选择已有字幕并返回”
字幕提取应该发生在资源整理/上传 115 之前，或者由独立离线系统完成
```

## 关键结论

对 115 `strm` 来说，**不要在播放链路上做任何需要读取原视频容器的动作**。

包括但不限于：

```text
动态提取内嵌字幕
动态生成缩略图
动态读取章节信息
动态读取媒体详细信息
动态分析音轨/字幕轨道
动态探测 HDR/DV/音频布局
```

这些在本地盘上都很正常，但放到 115 远程文件上，就会变成高成本随机读/顺序读，甚至近似完整下载。

所以代理层应该有一个明确原则：

```text
115 strm 播放链路只服务“已知的、已缓存的、已落地的元数据和资源”
```

## 关于 1：刮削时不适合批量提取

完全同意。

如果“刮削”发生在 Emby 已经只看到 `strm` 之后，那这个阶段再提取字幕就晚了。

因为这时字幕提取的输入已经变成：

```text
Emby/代理 -> 115 远程视频
```

这和播放时提取没有本质区别。大量文件批量处理会更危险：

```text
大量下载
大量 Range 请求
大量 ffmpeg 探测
高概率触发 115 风控
```

所以字幕提取的合理时机不是“入 Emby 库之后”，而是：

```text
本地整理资源阶段
上传 115 前
资源还在本地磁盘时
```

这个阶段可以做：

```text
读取 mkv/mp4
提取内嵌字幕
提取章节
生成 nfo
生成 poster/fanart
生成 preview 缩略图
整理命名
上传视频 + 外挂字幕 + 元数据
```

也就是说，**115 应该只承载整理后的成品资源**，而不是让 Emby 后期再从 115 视频里挖信息。

## 关于 2：拦截后多字幕返回哪条

这里要分清楚两类字幕请求。

### 情况 A：请求的是具体字幕轨道

你给的 URL 是：

```text
/Subtitles/3/0/Stream.ass
```

这里的 `3` 一般代表 Emby 里某个 subtitle stream index。

这类请求不是“随便给我一条字幕”，而是：

```text
客户端已经选择了第 3 条字幕
服务端负责返回第 3 条字幕的内容
```

所以代理如果拦截，就不能盲目返回任意字幕。它需要知道：

```text
Emby 的 subtitle stream index 3 对应哪一个本地外挂字幕文件
```

如果不知道，就应该拒绝或返回空，而不是猜。

### 情况 B：请求的是字幕列表/媒体详情

在用户选择字幕之前，Web 端通常会先拿到媒体详情，里面有 `MediaStreams`，例如：

```json
{
  "Type": "Subtitle",
  "Index": 3,
  "Language": "chi",
  "DisplayTitle": "Chinese Simplified - ASS",
  "IsExternal": false
}
```

真正可控的地方其实是这里。

也就是说，代理不应该只在 `/Subtitles/.../Stream.ass` 阶段拦截，还应该考虑在“媒体详情返回阶段”处理字幕列表。

更合理的策略是：

```text
对 115 strm：
隐藏内嵌字幕轨道
只暴露本地已存在的外挂字幕轨道
```

这样用户在前端根本不会选到那个会触发 ffmpeg 的内嵌字幕。

## 多外挂字幕怎么处理

如果已有多个外挂字幕，应该让 Emby/客户端继续选择，而不是代理自己决定。

例如本地有：

```text
Movie.zh-CN.ass
Movie.zh-TW.ass
Movie.en.srt
Movie.ja.ass
```

那么理想状态是 Emby 的字幕列表里显示：

```text
简体中文
繁体中文
English
Japanese
```

用户选哪条，代理就返回哪条。

代理要做的是维护映射关系：

```text
Subtitle Index 4 -> Movie.zh-CN.ass
Subtitle Index 5 -> Movie.zh-TW.ass
Subtitle Index 6 -> Movie.en.srt
```

而不是：

```text
请求任何字幕 -> 返回默认中文字幕
```

后者会造成错语种、错轨道、错显示名。

## 代理层的正确职责

我建议代理层做三件事。

### 1. 禁止 115 strm 动态读取视频提取资源

拦截这些危险行为：

```text
/Subtitles/{index}/.../Stream.*
/Images/Primary?...
/Videos/.../Thumbnail...
/Videos/.../Chapters...
/Items/.../PlaybackInfo 里触发 ffprobe 的路径
```

具体哪些要拦，需要看项目当前代理了哪些 Emby API。但原则是：

```text
凡是需要 Emby/ffmpeg 重新打开视频文件分析的，都不应该走 115 原视频
```

### 2. 媒体详情里隐藏不可安全使用的内嵌字幕

对于 115 `strm`：

```text
IsExternal = false 的字幕轨道
```

最好从返回给 Web 的 `MediaStreams` 里移除，或者标记为不可用。

只保留：

```text
IsExternal = true
Path 指向本地字幕文件
```

这样前端不会发起危险字幕请求。

### 3. 字幕请求只返回已知外挂字幕

当请求：

```text
/Subtitles/{index}/0/Stream.ass
```

代理检查：

```text
这个 index 是否对应本地外挂字幕
```

如果是，返回。

如果不是，拒绝：

```text
404
204
或者返回一个空字幕文件
```

我更倾向于 `404` 或空字幕，取决于前端兼容性。

## 你第 3 点的方向是对的

你说：

> 整理资源上传到115的时候可以提取字幕，后期可以做程序监控文件自动提取？当然，不是做在这个项目上。

这就是我认为最优雅的架构。

可以拆成两个系统：

```text
资源整理系统：
负责重活，处理本地视频，提取字幕/章节/元数据，然后上传 115

播放代理系统：
负责轻活，只转发播放请求，只返回已有资源，不做重分析
```

这样职责非常清晰。

资源整理系统可以慢，可以排队，可以失败重试，可以占 CPU，可以跑 ffmpeg。

播放代理系统必须快、轻、稳定，不能一不小心触发几十 GB 的远程读取。

## 这对当前项目意味着什么

当前项目里，不应该做：

```text
当用户点字幕时，自动去 115 视频里提取
当找不到字幕时，fallback 到 ffmpeg 提取
当字幕 index 不匹配时，猜一条返回
```

应该做：

```text
识别 115/strm 媒体
只暴露外挂字幕
阻止内嵌字幕动态提取
对缺失字幕明确失败
```

也就是说，当前项目更像一个“安全播放代理”，不是“资源加工器”。

## 最终建议

我会把策略定成这样：

```text
115 strm 模式下：
1. 禁用内嵌字幕动态提取
2. 媒体详情中隐藏内嵌字幕轨道
3. 只保留 Emby 已识别到的外挂字幕
4. 字幕请求只允许命中外挂字幕文件
5. 没有外挂字幕就认为没有字幕
```

如果未来有独立资源整理器，它负责保证上传到 115 前已有：

```text
video.strm
video.zh-CN.ass
video.zh-TW.ass
video.en.srt
video.nfo
poster.jpg
fanart.jpg
```

那么当前代理只要安全地把这些“已存在资源”提供给 Web 端就够了。





方案内容：

1. **识别 115/strm 媒体**
   判断当前视频是否属于远程 115 资源。

2. **隐藏内嵌字幕轨道**
   在媒体详情/播放信息返回时，移除 `IsExternal = false` 的字幕。

3. **只保留外挂字幕**
   仅展示 Emby 已识别到的 `.ass` / `.srt` / `.vtt` 等外挂字幕。

4. **拦截字幕流请求**
   对 `/Subtitles/{index}/.../Stream.*` 做校验。

5. **只允许外挂字幕返回**
   请求的字幕 index 必须对应已知外挂字幕，否则拒绝。

6. **禁止 ffmpeg 动态提取**
   不允许因字幕请求触发读取原视频文件。

7. **缺失字幕直接失败**
   没有外挂字幕就返回无字幕，不 fallback 到内嵌提取。

8. **保留后续扩展空间**
   外部资源整理程序负责上传前提取字幕，本项目只消费已有字幕。

外挂字幕导出时，建议按 **主文件名 + 语言 + 可选标题 + 扩展名** 命名。

推荐格式：

```text
视频主名.zh-CN.ass
视频主名.zh-TW.ass
视频主名.en.srt
视频主名.ja.ass
```

如果想保留字幕轨道标题，可以加在语言后面：

```text
视频主名.zh-CN.简日双语.ass
视频主名.zh-TW.繁日双语.ass
视频主名.en.English.ass
```

以你的例子：

```text
天国大魔境 - S01E01 - 天国と地獄.strm
```

可以导出为：

```text
天国大魔境 - S01E01 - 天国と地獄.zh-CN.简日双语.ass
天国大魔境 - S01E01 - 天国と地獄.zh-TW.繁日双语.ass
天国大魔境 - S01E01 - 天国と地獄.en.English.srt
```

## 推荐优先级

最稳的是：

```text
视频主名.zh-CN.ass
```

显示名更好的是：

```text
视频主名.zh-CN.简日双语.ass
```

但不同媒体服务器/刮削器对“额外标题段”的识别不一定完全一致。

所以我建议导出器默认用：

```text
视频主名.zh-CN.ass
视频主名.zh-TW.ass
视频主名.en.srt
视频主名.ja.ass
```

如果要保留标题，可以在字幕文件内部写 `Title`，或者作为可选模式输出：

```text
视频主名.zh-CN.forced.ass
视频主名.zh-CN.default.ass
```

## 语言代码建议

常用：

```text
.zh-CN     简体中文
.zh-TW     繁体中文
.en        English
.ja        Japanese
.ko        Korean
```

也可以用 Emby/ISO 风格：

```text
.chi       Chinese
.cht       Traditional Chinese
.eng       English
.jpn       Japanese
.kor       Korean
```

我更建议用：

```text
.zh-CN
.zh-TW
.en
.ja
```

可读性更强。

## 导出策略

从内嵌字幕轨道导出时，用轨道信息生成文件名：

```text
baseName + "." + language + "." + title + "." + ext
```

其中：

```text
baseName = 视频/strm 主文件名
language = 根据轨道 Language 映射
title = 清理后的 Title，可选
ext = ass/srt/vtt
```

如果没有语言：

```text
视频主名.und.ass
```

如果多条同语言：

```text
视频主名.zh-CN.ass
视频主名.zh-CN.2.ass
```

或：

```text
视频主名.zh-CN.简日双语.ass
视频主名.zh-CN.简体.ass
```

## 最终建议

资源整理/上传前的字幕导出程序可以默认生成：

```text
视频主名.{语言代码}.{标题可选}.{扩展名}
```

例如：

```text
天国大魔境 - S01E01 - 天国と地獄.zh-CN.简日双语.ass
```

如果怕兼容性问题，就用最稳格式：

```text
天国大魔境 - S01E01 - 天国と地獄.zh-CN.ass
```
